Case Study · Work in Progress

Global Luggage Delivery Operations Transformation

From fragmented, manually coordinated fulfilment to an owned booking platform, integrated OMS/TMS, distributor APIs, automated dispatch, event-driven status updates and exception-led operations.

Business Transformation Process Redesign OMS / TMS API Integration Applied AI Service Operations

Transformation objective

Redesign the end-to-end luggage-delivery operation so that orders from direct and distributor channels enter one controlled operating system, routine decisions and status updates are automated, suppliers execute against structured jobs, and CS / Operations focuses primarily on exceptions.

As-Is boundary Customer books through the direct website or an OTA / distributor channel → service is fulfilled → final handover evidence is recorded.
To-Be ambition Own the booking experience and the operational system of record, while integrating distributors, logistics partners, payments and communication channels through APIs and lightweight partner interfaces.

Success measures

Manual touchpoints per booking
Operations handling time per booking
Exception-resolution time
SLA adherence and customer-update latency

Baseline values remain TBD until measured from operational data.

Before — current operating model

Core pattern
Customer / OTA→ Email / OTA backend→ CS / Operations→ Ecwid / Google Sheet→ Email / supplier chat→ Supplier / Driver
Manual order normalization Distributor bookings may require CS to log into an OTA backend, retrieve booking details, validate them, and manually recreate the order through the internal Ecwid flow.
CS as communication relay Customers communicate through email / Respond.io while suppliers use email, WhatsApp, LINE or WeChat. CS manually moves status information between both sides.
Manual supplier dispatch Supplier choice depends on staff knowledge or spreadsheets. Orders are manually cleaned, forwarded, confirmed and chased across multiple channels.

What the diagnosis showed

Fragmented system of record Order state is distributed across the e-commerce layer, Google Sheets, Gmail, OTA systems, messaging tools and supplier channels.
Tacit operational knowledge Important exception logic, routing preferences and contextual judgement are not fully represented as maintained system rules.
Key-person dependency Non-standard decisions frequently require escalation to experienced Operations staff.
No structured dispatch control loop Assignment, acceptance, non-response, fallback and service-day status do not run through one controlled workflow.
Design implication

The target state should not merely automate email forwarding. It needs a proper transaction core: one booking / shipment record, a lifecycle state model, a maintained rules layer, structured partner execution and an exception-management workspace.

After — target operating model

The recommended future state follows the way modern logistics and commerce platforms separate the customer channel, transaction core, integration layer, partner execution and exception-management functions.

1 · Owned customer booking layer
Responsive web booking Serviceability check Dynamic service options Stripe payment Secure tracking link

Own the booking experience and booking API. Keep commodity services such as payment processing external rather than rebuilding them.

2 · Distributor integration layer
REST APIs Webhooks Scheduled API sync CSV / email fallback adapters Canonical data mapping

Klook, KKday and other distributors should create or update orders directly in the internal platform without manual re-entry wherever integration capability exists.

3 · Owned OMS / TMS core — system of record
Canonical Order ID Customer & itinerary Shipment / bag records Status state machine SLA timestamps Supplier assignment Fees / adjustments Exception state Audit history

Every booking, regardless of source, resolves to one structured record. Email becomes a notification channel rather than the operational database.

4 · Rules & master-data layer
Service areas Airport timing rules Lead times Supplier capabilities Route eligibility Pricing references Escalation rules Version history

Move repeatable operating rules out of memory and scattered spreadsheets into maintained configuration that the workflow can execute.

5 · Dispatch & partner execution
Supplier ranking Auto-dispatch Accept / reject timer Fallback supplier Manual override Partner API Partner portal / secure job link

Mature partners can integrate by API; smaller partners can use a lightweight mobile web interface or secure job link. A dedicated driver app is not mandatory.

6 · Event-driven communication
Booking confirmed Supplier assigned Customer ready Picked up Delivered Delay / exception Email Messaging integration

Customers receive status automatically from structured events. CS no longer has to manually relay routine “arrived”, “picked up” or “delivered” messages.

7 · Exception control tower
Exception queue Severity / priority Owner SLA clock Recommended action Escalation Resolution log

CS / Operations shifts from monitoring every normal order to managing only cases that require intervention.

8 · Chain of custody & proof of service
Pickup evidence Bag / tag ID Recipient verification OTP / QR where appropriate Delivery evidence Timestamp / location metadata

Proof should establish not only that a handover happened, but that it occurred to the correct party.

9 · Data, analytics & process intelligence
Event log Cycle time Manual touchpoints Supplier acceptance SLA adherence Exception rate Customer update latency

A structured event history makes operational performance measurable and enables process mining rather than relying on anecdotal diagnosis.

10 · AI assistance layer
Intent extraction Missing-information detection Exception classification Knowledge retrieval Case summarization Response drafting

AI assists around the transaction core. It should not be the source of truth and should not autonomously approve high-risk policy, payment or recipient-verification decisions.

11 · Governance & access control
Role-based access PII controls Audit log Rule ownership Change history Human override

What should be owned vs integrated

Own Booking UX and booking API; OMS/TMS transaction core; canonical data model; lifecycle state; rules and supplier master data; dispatch logic; exception workspace; operational event log; chain-of-custody controls.
Integrate rather than rebuild Payment processing, email delivery, messaging providers, mapping / geocoding, OTA channels, mature logistics-partner APIs, identity / OTP services and analytics tooling where appropriate.

Human vs Automation vs AI decision matrix

The target model separates work by decision type rather than applying AI everywhere. Deterministic rules handle repeatable operational logic, AI handles ambiguity and unstructured information, and humans retain control where judgement, policy, safety or commercial authority is required.

Decision rule

Automate when the input is structured and the rule is stable. Use AI when the input is unstructured or contextual. Keep a human in control when the decision is high-risk, policy-sensitive, irreversible or commercially discretionary.

Process step Primary owner Role of automation Role of AI Human control / guardrail
Direct / OTA booking ingestion Automation Create canonical order, map fields, deduplicate, assign source and timestamps. Fallback extraction when source data arrives in semi-structured email or documents. CS reviews failed mappings or incomplete orders.
Serviceability & timing validation Automation Execute city, lead-time, airport timing, product-type and required-field rules. Interpret ambiguous addresses or customer-written notes when structured validation is insufficient. Operations approves unclear or policy-edge cases.
Missing-information follow-up Automation + AI Detect missing required fields and trigger follow-up workflow. Draft context-aware request using order history and customer language. Human review only for non-standard or sensitive cases.
Supplier eligibility & ranking Automation Filter by service area, capability, timing, route, cost rules and availability; rank eligible suppliers. Optional explanation of why a route is unusual or why historical supplier behavior differs. Operations can override assignment with reason captured.
Supplier dispatch Automation Generate structured job, send through API / portal / secure link, start acceptance timer, trigger fallback. No AI required for normal dispatch. Human intervention for no-capacity, RFQ or special-service cases.
Supplier confirmation & reminder Automation Track accept / reject / timeout state and send reminders or escalate automatically. Interpret free-text supplier replies if structured response is unavailable. Operations resolves ambiguous replies.
Customer service-day updates Automation Trigger notifications from structured events such as ready, picked up, delayed and delivered. Adapt wording / language and summarize relevant context. CS handles complaints, disputes or unclear status.
Inbound customer messages AI + Automation Attach message to correct order and route to workflow. Classify intent, extract requested change, detect urgency, summarize conversation and retrieve relevant rule. CS approves actions that alter service, fees or policy.
Operational exception triage AI-assisted Human Create case, start SLA clock, collect order / supplier / customer context. Classify exception, summarize evidence, retrieve playbook and propose next action. Operations makes the actual exception decision.
Fee waiver / refund / policy exception Human Calculate standard entitlement where rules are explicit. Summarize case and surface comparable precedent. Authorized manager approves discretionary outcome.
Chain of custody / recipient handover Automation + Human control Use OTP / QR / tag verification, timestamps and evidence requirements. Optional photo-quality or evidence-completeness checks. AI does not independently decide recipient identity or release luggage in high-risk cases.
Knowledge retrieval AI Maintain versioned rule and supplier data sources. Retrieve the most relevant operational rule, supplier condition or exception playbook for the current case. Responses must cite the governed source; staff can escalate conflicting rules.
Performance monitoring Automation Calculate SLA, cycle time, rework, acceptance, exception and communication-latency metrics. Summarize recurring patterns and highlight anomalous process variants. Managers validate conclusions before changing policy or supplier strategy.

AI guardrails

AI is not the system of recordThe OMS/TMS owns booking state, money, supplier assignment and operational timestamps.
Structured rules beat AI where possibleServiceability, time windows, pricing formulas and eligibility should be deterministic when the policy is known.
Ground AI in governed knowledgeOperational answers should retrieve from maintained rules, supplier data and approved playbooks rather than rely on model memory.
Escalate uncertaintyLow-confidence extraction, conflicting rules, policy exceptions and safety-sensitive decisions route to a human.

What this demonstrates

AI business analysis is not “add a chatbot.”

This design starts from process decomposition, separates deterministic logic from judgement, defines where AI actually adds value, preserves human authority for high-risk decisions, and connects the AI layer to an auditable transaction core. That is the operating model required to move an AI concept into a production business process.

Requirements & controls

Translate the To-Be model into business requirements, functional requirements, non-functional requirements, acceptance criteria, data requirements and UAT scenarios — starting with booking intake and normalization.

Requirements — Booking Intake & Normalization

This first requirements slice translates the target architecture into implementation-ready business analysis for the point where direct and distributor bookings enter the operating system.

Business requirements

IDRequirementBusiness rationale
BR-01 All direct and distributor bookings must resolve to one canonical internal order record. Remove duplicate manual order creation and create one source of truth for downstream operations.
BR-02 The booking source must not determine how Operations processes the order after normalization. Website, Klook, KKday and future channels should enter the same fulfilment workflow once mapped.
BR-03 Routine booking ingestion and validation should require no CS intervention when required data is complete and rules are satisfied. Move CS effort away from data entry and toward true exceptions.
BR-04 No booking may disappear silently between an external channel and the internal OMS/TMS. Every ingestion attempt must have an auditable success, exception or failure state.
BR-05 Channel-specific differences must be absorbed by the integration layer rather than by frontline staff. Reduce process variation, training burden and transcription risk.

Functional requirements

IDSystem behavior
FR-01The platform shall accept direct bookings from the owned booking interface and distributor bookings through API, webhook, scheduled sync or controlled fallback ingestion.
FR-02The integration layer shall map each source schema into a canonical order model before the order enters fulfilment.
FR-03The platform shall generate one unique internal Order ID and preserve the original external source and external Order ID.
FR-04The platform shall prevent duplicate creation when the same external booking is received more than once.
FR-05The platform shall validate required fields such as service date/time, city, service type, customer identity/contact details, pickup/delivery location, and route-specific airport/flight information where applicable.
FR-06The platform shall run deterministic serviceability and timing rules immediately after normalization.
FR-07Orders that pass validation shall progress automatically to the next fulfilment state without manual re-entry.
FR-08Orders with missing, conflicting or non-compliant data shall enter a structured exception queue with the failed rule and required next action.
FR-09Where source data arrives in semi-structured email or documents, AI-assisted extraction may propose field values, but low-confidence or conflicting fields must require human confirmation.
FR-10Every create, update, validation result, exception and manual override shall be timestamped in the audit history.

Canonical data requirements

Order identity Internal Order ID, source channel, source Order ID, booking timestamp, current lifecycle status.
Customer Name, email, contact number, preferred communication channel / app where captured.
Service Service date, service time, city, service type, pickup type, delivery type.
Locations Hotel / property name, address, airport, terminal, relevant location notes.
Travel context Flight number and route-specific timing information where applicable.
Operational metadata Validation result, failed rule, assigned supplier, SLA timestamps, exception status and audit trail.

Non-functional requirements

IDRequirement
NFR-01Reliability: ingestion must be retryable and idempotent so retries do not create duplicate orders.
NFR-02Observability: failed integrations, schema-mapping errors and validation failures must be visible in an operational dashboard / queue.
NFR-03Auditability: the system must retain who/what changed an order, the previous value, the new value and timestamp.
NFR-04Security: customer PII must be role-restricted, and integrations must use controlled credentials rather than personal accounts.
NFR-05Maintainability: source mappings and business rules should be configurable without rewriting the full application wherever practical.
NFR-06Extensibility: adding a new distributor should require a new adapter / mapping, not a new fulfilment process.
NFR-07Performance: normal automated booking ingestion and validation should complete within an agreed operational threshold; exact SLA to be defined during implementation.

Acceptance criteria

AC-01 · Website bookingA valid direct booking creates exactly one canonical OMS/TMS order with the correct source metadata and proceeds without CS re-entry.
AC-02 · Distributor bookingA valid distributor booking produces the same canonical internal structure as a direct booking while preserving the distributor Order ID.
AC-03 · Duplicate eventReceiving the same external booking twice updates or ignores the duplicate according to policy and never creates a second active order.
AC-04 · Missing fieldA booking missing a required contact / route field is stopped before dispatch and appears in the exception queue with a clear reason.
AC-05 · Rule failureA booking outside a configured service area or timing rule does not progress silently and is routed to the correct exception workflow.
AC-06 · Audit trailAn Operations user can reconstruct how the booking entered the system, what validation ran, what changed and who approved any override.

Representative UAT scenarios

ScenarioGivenWhenThen
UAT-01 · Happy-path direct booking All mandatory website fields are valid. Customer completes payment and booking. One canonical order is created, validation passes and the order advances automatically.
UAT-02 · Happy-path KKday booking KKday sends a complete supported booking payload. The integration receives it. Fields are mapped correctly, the KKday Order ID is retained, and no CS copy/paste is required.
UAT-03 · Missing flight information An airport-related booking requires flight data but the source does not supply it. Validation runs. The order enters the exception queue and a missing-information workflow is triggered.
UAT-04 · Duplicate OTA delivery An external channel retries the same booking event. The same source Order ID is received again. No duplicate active order is created and the event is logged.
UAT-05 · Non-serviceable address The destination fails the configured service-area rule. Validation runs. The booking is held, the failed rule is visible, and Operations is given the appropriate resolution path.
UAT-06 · AI extraction uncertainty A fallback email contains an ambiguous hotel address. AI-assisted extraction returns low confidence or conflicting candidate values. The system does not auto-approve the field and requires human confirmation.

Control design

Normal flow should be touchless; uncertainty should be visible.

The objective is not to remove humans from operations. It is to make routine orders deterministic and auditable so human attention is concentrated on incomplete, ambiguous, non-compliant or high-risk cases.
